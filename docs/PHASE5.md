# Phase 5 결과: 호환성, 창, 패키징

2026-11-02

> "파일마다 창 하나"는 Phase 5를 마친 뒤 사용자 피드백으로 **한 창 안의 탭**으로 바뀌었다. 맨 아래 "Phase 5 이후 피드백"을 참고.

## 결정 (Phase 시작 시 사용자 선택)

- **기존 주석 복구: 하지 않음.** Phase 0에서 확인한 실제 깨짐은 FreeText가 아니라 Acrobat Fill & Sign이 페이지 내용에 평탄화한 글자였다. 다른 프로그램의 FreeText와 Fill & Sign 글자는 그대로 보여 주기만 하고, 앞으로의 타이핑은 이 앱으로 한다. SPEC에 반영함
- **실행 중 다른 PDF 열기: 새 창.** 파일마다 창 하나

## 구현한 것

| 영역 | 내용 |
|---|---|
| 파일마다 창 하나 | `tauri-plugin-single-instance`로 두 번째 실행(.pdf 더블클릭, 명령줄)을 첫 프로세스가 받음. 그 파일을 연 창이 있으면 그 창을 앞으로 가져오고(경로 대소문자·표기 무관), 문서가 없는 창이 있으면 그 창에서, 아니면 새 창에서 엶. 창 안에서 최근 파일, 열기, 끌어 놓기로 다른 창에 이미 열린 파일을 열면 그 창을 앞으로 가져옴. 상대 경로는 실행한 폴더 기준으로 풀림. 새 창은 main 창 설정을 그대로 씀(핀치 줌 포함) |
| 호환성 corpus | `src/pdf/engine/corpus.ts`: 파일 구조 변형 7가지(classic xref, xref stream + object stream, AES-256·RC4-128 소유자 암호만, startxref가 깨진 파일, /Rotate·/MediaBox를 페이지 트리에서 상속, 다른 프로그램 주석 + 간접 /Annots)와 앱과 같은 편집 왕복(상자 2개 + 하이라이트 → 저장 → 다시 열어 수정·이동·삭제·색 변경·하이라이트 추가 → 저장) |
| 렌더 비교 | `tools/compat-render.ts`: corpus와 samples의 편집 결과를 MuPDF(이 앱), poppler, PDFium(Chrome·Edge의 엔진), pdf.js(Firefox의 엔진)로 2배 렌더해서 앱 주석의 위치와 색을 비교하고, 엔진별 잘라낸 그림을 나란히 붙인 contact sheet를 만듦. PDFium(`@hyzyla/pdfium`)과 pdf.js(`pdfjs-dist`)는 개발 의존성 |
| 설치 파일 | NSIS, 사용자 단위 설치(관리자 권한 없음), 설치 화면 한국어. `.pdf`를 "연결 프로그램" 목록에 등록 |

## 검증

- **단위 테스트**: 기존 55개 + 호환성 왕복 7개(파일 구조 변형마다)
  - 저장 방식: 깨진 파일은 첫 저장만 full(repair 후), 그 뒤는 incremental. 나머지는 모두 incremental이고 원본 바이트가 앞부분에 그대로 남음
  - 다시 열 때 repair가 필요 없음. 암호 걸린 파일은 저장 후에도 암호가 유지됨
  - 상자와 하이라이트가 쓴 그대로 읽힘. MuPDF가 상자 AP에서 뽑은 글자가 원문과 같음(암호 파일의 복호화 포함)
  - 다른 프로그램의 주석(FreeText, Highlight, 메모)은 개수와 종류가 그대로
- **Rust 테스트**: 기존 4개 + 창 2개(명령줄 PDF 인자 해석, 대소문자가 다른 같은 파일 판별)
- **창 동작** (`tools/window-test.mjs`, 실제 앱을 여러 번 실행): 8단계 모두 기대대로
  1. 파일 없이 실행 → 빈 창 하나
  2. a.pdf 실행 → 빈 창이 a.pdf를 엶(창 1개)
  3. b.pdf 실행 → 새 창(창 2개)
  4. `A.PDF`(대문자 경로) 실행 → 창이 늘지 않고 a 창이 앞으로
  5. b 창에서 a.pdf를 열면 b는 그대로이고 a 창이 앞으로
  6. b 창을 닫은 뒤 b.pdf 실행 → 다시 새 창
  7. 상대 경로 `c.pdf`로 실행 → 실행한 폴더의 c.pdf가 새 창에서 열림
  8. 두 번째 실행 프로세스는 매번 바로 종료됨(exit 0)
- **렌더 엔진 비교** (`tools/compat-render.ts`, 7개 변형 + samples 2개, 2배 렌더): 앱 주석의 경계 차이가 MuPDF 대비 poppler, PDFium, pdf.js 모두 **최대 1 px**. 하이라이트 평균 색 차이는 채널당 3 이하. contact sheet에서 한글 상자가 네 엔진에서 같은 모양으로 보임(회전 쪽, 실제 Acrobat 파일 포함)
- **release 빌드** (`npm run tauri build`, 처음 5분 47초. 대부분 의존 crate 최초 컴파일과 LTO 링크): `typenote.exe` 14.4 MB, 설치 파일 `src-tauri/target/release/bundle/nsis/typenote_0.1.0_x64-setup.exe` 7.97 MB
- **release 빌드 실제 동작** (`tools/release-test.mjs` + `run-app.ps1 -Release`, dev 서버 없이 DOM과 실제 입력만): 파일이 열리고 비트맵이 그려짐, dev hook 없음, 오류 배너 없음. 텍스트 도구로 "릴리스 빌드 확인 Release 123" 입력, 하이라이트 드래그, 자동 저장("저장됨"). 저장된 파일에 FreeText(Pretendard subset `FontFile2` embed)와 하이라이트(청록 40%)가 들어 있음. CSP, wasm, worker, 폰트 asset이 release에서도 정상

## 직접 확인할 것

설치:

- ☐ `src-tauri/target/release/bundle/nsis/typenote_0.1.0_x64-setup.exe` 실행. 코드 서명이 없어서 "Windows의 PC 보호" 창이 뜨면 "추가 정보" → "실행". 관리자 권한은 묻지 않음
- ☐ PDF 오른쪽 클릭 → "연결 프로그램"에 typenote가 보이는지. 기본 앱으로 쓰려면 "다른 앱 선택"에서 typenote를 고르고 "항상"을 누름(Windows 11은 앱이 기본 앱을 스스로 바꿀 수 없음)
- ☐ 앱이 켜져 있을 때 다른 PDF를 더블클릭하면 새 창이 뜨는지, 이미 연 PDF를 다시 더블클릭하면 그 창이 앞으로 오는지(Windows 포커스 규칙상 작업 표시줄만 깜빡일 수도 있음)

다른 뷰어 (`spike/out/compat/`에 앱으로 편집한 파일이 있음. `sample-*.pdf`는 samples 복사본에 편집한 것):

- ☐ Acrobat에서 한글 상자("수정된 상자 Edited / 둘째 줄 그대로")가 Pretendard로 보이고, 하이라이트(노랑 60%, 청록 40%)가 앱과 같은 색인지
- ☐ Acrobat에서 하이라이트를 선택하고 색을 바꾸거나 지울 수 있는지. 그렇게 저장한 파일을 앱에서 다시 열었을 때 상자가 그대로이고 편집할 수 있는지
- ☐ 암호 파일(`aes256-owner-only.pdf`, `rc4-128-owner-only.pdf`)이 Acrobat에서 암호 없이 열리고 상자가 보이는지
- ☐ Edge나 Chrome에서 같은 파일(엔진 비교는 PDFium으로 했지만 실제 브라우저에서도 한 번)

## 알려진 한계

- 코드 서명이 없어서 설치할 때 SmartScreen 경고가 뜸
- 자동 업데이트 없음. 새 버전은 설치 파일을 다시 실행하면 덮어씀
- 사용자 암호(열 때 암호를 묻는 PDF)는 여전히 지원하지 않음. 소유자 암호만 걸린 파일은 지원하지만, 그 파일의 권한 설정(주석 수정 금지 등)은 따르지 않음
- linearized PDF는 MuPDF가 더 이상 만들 수 없어 corpus에 없음. incremental 저장하면 linearize가 풀리는 것은 정상이고 읽기에는 영향이 없음
- 창마다 MuPDF worker가 따로 떠서, 창 하나당 메모리를 따로 씀
- 창 크기와 위치는 기억하지 않음. 새 창은 Windows 기본 위치에 뜸
- Acrobat 동작은 자동으로 확인하지 못함(위 체크리스트)

## Phase 5 이후 피드백

설치한 앱을 써 본 뒤 받은 요청들. 사용자 선택: 앱 안에서 열어도 새 탭, 하이라이트는 "글자 높이에 딱 맞게".

| 요청 | 구현 |
|---|---|
| 한 창 안의 여러 탭 (Acrobat처럼) | 새 창은 만들지 않음. 열기, 최근 파일, 끌어 놓기, 탐색기 더블클릭, 명령줄 모두 새 탭(이미 열린 파일이면 그 탭으로). 여러 파일을 한 번에 넘기면 넘긴 순서대로 탭이 생김. 탭마다 worker와 DocStore가 따로 있고(닫으면 worker 종료로 메모리 반환), 쪽, 배율, undo 기록도 탭별. 닫기는 ×, 가운데 클릭, Ctrl+W(저장 후, 저장 못 하면 물어봄). Ctrl+Tab / Ctrl+Shift+Tab, Ctrl+PageDown / PageUp으로 이동. 저장 문제가 있는 탭에는 `!` 표시 |
| UI 영어 | 버튼, 메뉴, 툴팁, 상태, 배너, 확인 창, 엔진 오류 문구, 설치 화면 |
| 한글 자간만 살짝 줄이기 | 한글 글리프 뒤마다 −3% em. AP는 TJ 조정, overlay와 편집 textarea는 hmtx를 줄인 TTF 사본. 상자별 값(`/TypenoteTracking`)이라 그 전에 만든 상자는 편집할 때까지 그대로 |
| 하이라이트 세로 여백 제거 | 선택한 글자의 외곽선 높이에 맞춤. 글자가 없는 영역이면(그럴 일은 드묾) 원래 quad 그대로 |
| 스크롤바에 위치 표시가 없음 | 문서 전체 스크롤바: thumb이 쪽 위치를 보여 주고 끌면 쪽 이동(쪽 번호 표시), 빈 곳 클릭은 한 쪽 넘김, 스크롤바 위에서 휠도 동작 |
| 텍스트 도구에서도 윤곽선으로 이동 | 상자 윤곽선(안팎 몇 px)에서 이동 커서, 끌면 이동, 클릭만 하면 선택. 상자 안은 글자 커서 |
| 쪽 바깥 클릭으로 선택 해제 | 회색 영역을 누르면 입력 확정 후 상자와 하이라이트 선택 해제 |
| 클릭한 위치에 커서 | 상자를 클릭(선택 도구는 더블클릭)하면 그 위치에서 편집 시작. 편집 중 글자를 클릭하면 커서 이동(전에는 layer의 mousedown 처리 때문에 안 됐음) |
| 속성 바 때문에 가로 스크롤바 | 쪽 위의 막대는 쪽 안으로 밀어 넣고, 무엇이 삐져나와도 스크롤 영역이 넓어지지 않게 함 |
| (함께 고침) | dev 빌드를 설치된 앱과 분리(identifier `.dev`): 개발 중 실행이 사용 중인 앱에 파일을 넘기거나 최근 파일 목록을 공유하던 문제. 내 테스트 파일 10개가 최근 목록에 들어가 있던 것도 지움. release 빌드에서는 F5, Ctrl+R(새로 고침)로 탭이 날아가지 않게 막음. 툴바가 넘칠 때 저장 상태 글자가 줄어듦 |

검증:

- **단위 테스트 68개** (+6): 한글 자간(레이아웃 폭, TJ, overlay 폰트 advance, 저장·읽기·텍스트 추출), 글자 높이 하이라이트(정방향과 회전 쪽, 글자 없는 quad), 클릭 위치 → 커서
- **Rust 테스트 6개**: 명령줄 PDF 인자 여러 개, 열 파일 목록을 한 번만 넘김
- **탭** (`tools/tab-test.mjs`, 실제 앱을 여러 번 실행, 실제 키 입력): 12단계 모두 기대대로. 창은 항상 1개, 빈 상태 → a 탭 → b 탭 → `A.PDF`는 a 탭으로 이동 → 앱 안에서 b 열기는 b 탭으로 → b에 상자 추가 후 Ctrl+Tab으로 a, 뒤에서 b 자동 저장 → a에서 End로 3쪽, 탭을 오갔다 와도 3쪽 → Ctrl+W로 b 닫기 → b, c를 한 번에 넘기면 그 순서로 → 상대 경로 d.pdf
- **문서 스크롤바** (18쪽 샘플): 쪽 맞춤에서 thumb이 1/18 칸, 60% 지점까지 끌면 11쪽("11 / 18" 표시), 아래 빈 곳 클릭으로 12쪽
- **한글 자간 overlay와 AP 일치** (`tools/overlay-test.mjs`, 상자 3개 자간 있음): 좌우 0~1 px, 상하 0~2 px, 최적 정렬 IoU 0.92~0.95. 이전과 같은 수준
- **상자, 커서, 선택 해제, 속성 바** (실제 앱): 윤곽선 위 커서는 move, 안쪽은 text. 윤곽선을 끌면 이동하고 편집은 시작 안 함. 상자 안 클릭 → 커서 2, 편집 중 끝 쪽 클릭 → 커서 13. 쪽 바깥 클릭 → 선택 해제. 오른쪽 끝 상자의 속성 바 오른쪽 끝 = 쪽 오른쪽 끝, 가로 스크롤 0
- **하이라이트 높이**: test.pdf 첫 줄 62.6~83.9pt → 66.3~81.4pt. 실제 강의 PDF에서 줄마다 위 1~4.5pt, 아래(내림 글자 없는 줄) 1~5pt 줄어듦. 쪽 글리프 수집은 처음 한 번 8~31 ms
- **기존 시나리오** (`highlight-test.mjs`, `text-test.mjs`): 모두 통과. 다시 편집할 때 커서가 클릭 위치에 오도록 바뀌어 text-test의 E 단계는 Ctrl+End 후 입력으로 고침
- **설치 파일 다시 빌드** (3분 52초): `typenote_0.1.0_x64-setup.exe` 7.96 MB. release 빌드 실제 동작 확인(`release-test.mjs`)은 하지 않음: 사용자가 설치된 앱을 쓰는 중이었고, release 빌드는 그 앱과 identifier가 같아서 실행하면 테스트 파일이 사용자의 앱으로 넘어가기 때문. 같은 코드를 debug 빌드로 위 시나리오에서 확인함

직접 확인할 것:

- ☐ 새 설치 파일로 업데이트(앱을 닫고 실행). 설치된 앱에서 PDF 두세 개를 더블클릭해 한 창에 탭으로 쌓이는지
- ☐ 한글 자간 −3%가 마음에 드는지(더 줄이거나 늘리려면 `HANGUL_TRACKING` 한 줄)
- ☐ 하이라이트 높이, 스크롤바, 윤곽선 이동, 클릭 위치 커서가 손에 맞는지

알려진 한계:

- 탭 순서를 끌어서 바꾸는 기능은 없음. 앱을 다시 켜면 지난 탭은 열리지 않음
- 탭을 바꾸면 쪽은 기억하지만 쪽 안의 스크롤 위치(확대해서 보던 곳)는 기억하지 않음
- 글자 외곽선이 없는 텍스트(Type3 글꼴 일부 등)는 원래 높이로 칠함

## 디자인 개편

휠로 여러 쪽 넘기기(사용자 피드백: "쪽 맞춤에서 스크롤을 계속하면 계속 넘어가게, Acrobat처럼. 지금은 하나씩만 가고 빠르게 하면 아예 안 감"):

- 원인: 150ms 안에 이어지는 wheel 이벤트를 한 burst로 묶고 burst마다 최대 한 쪽만 넘겼음. 빠르게 여러 칸 굴리면 한 burst가 되어 첫 쪽 뒤로는 모두 무시됨. 게다가 폭 맞춤처럼 쪽이 화면보다 긴 경우, 175% 배율에서 scrollTop이 58.3/59처럼 소수 픽셀에서 멈추는데 쪽 끝 판정 여유가 0.5px이라 끝으로 인정되지 않아 휠과 ↓ 모두 다음 쪽으로 넘어가지 않았음
- 바꾼 것: 쪽 끝에서 마우스 휠 한 칸마다 한 쪽(한 이벤트에 두 칸이면 두 쪽), 터치패드는 250px마다 한 쪽. 긴 쪽은 먼저 쪽 안을 스크롤하고, 터치패드 관성은 예전처럼 쪽 끝에서 멈춤. 화면이 따라오기 전의 연속 넘김은 이어 셈(300ms). 쪽 끝 판정 여유 1.5px
- 확인(실제 앱, 18쪽): 쪽 맞춤에서 휠 5칸(20ms 간격) 1→6쪽, 3칸(5ms) 6→9, 8칸(2ms) 1→9, 위로 4칸 9→5. 신뢰 휠 이벤트(CDP)도 칸으로 인식. 터치패드처럼 25px×30번 → 3쪽. 폭 맞춤(쪽이 59px 더 김)에서 휠 6칸: 쪽 끝까지 스크롤, 다음 쪽, … 1→4쪽. ↓도 쪽 끝에서 다음 쪽. 단위 테스트 70개
